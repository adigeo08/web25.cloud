                                View technical details
                                
1 · WEB25 bundle

                                
Deterministic in-memory bundle. In gzip mode the whole site becomes site.bundle.json.gz.

                                


                                
2 · .torrentchain payload

                                
The signed WEB25 provenance manifest, inserted into the torrent before it is created.

                                


                                
3 · EVM signature

                                
Proves the WEB25 publisher. Produced once per website, when .torrentchain is generated — never again for registry publication.

                                


                                
4 · Torrent artifact

                                
The BitTorrent infohash identifies the distributed artifact. Website content travels over BitTorrent, not over Nostr.

                                


                                
5 · NIP-35 registry event

                                

                                    Signed with the Nostr identity derived from the same wallet key. This signature proves
                                    who published the registry entry; the EVM signature above proves who published
                                    the website. Two separate signatures, two separate claims.
                                

                                


                                
6 · Per-relay publication results

                                
DTAN and the other registry relays. Discovery only — never a source of authenticity.

☁️ About WEB25.cloud

                        

                            WEB25.cloud is a
                            PeerWeb fork
                            focused on local EVM identity, signed static-site deploys, and direct peer-to-peer messaging
                            addressed by Nostr. Core flows are browser-native: no backend, no signalling server and no
                            mandatory MetaMask connection. The browser talks directly to STUN, WebTorrent and public
                            Nostr relays.
                        

                    


                    

                        
🪪 Identity: one local key, three addresses

                        

                            The identity model is local-first and is inspired by
                            mylofi/local-data-lock:
                            key material stays in-browser and WebAuthn passkeys gate unlock/signing sessions.
                            A single secp256k1 key backs all three identities shown on the Identity page —
                            there is no second seed and no second private key.
                        

                        

                            
🏷️ EVM address for signing deploys — 0x…

                            
🔑 ECIES public key for encrypted messaging — 04…

                            
🪐 Nostr address for being reached by others — npub1…

                            
🔐 Local wallet, no mandatory external wallet extension

                            
🧬 WebAuthn unlock with Face ID / Touch ID / device PIN

                            
🧹 Session key lifecycle with explicit lock/clear behavior

                        

                        

                            The Identity page shows all three side by side, each with its own copy button.
                            The Nostr address can be added or removed there: removing it takes you off the
                            relays and hides the address, and adding it back restores the same
                            npub — because it was never a separate key to begin with.
                        


                        


                        
📦 Publishing: Bundle pipeline + .torrentchain

                        

                            Static-site deploys run through a bundle pipeline (default: gzip), then attach a signed .torrentchain
                            manifest carrying publisher identity and integrity metadata.
                        

                        

                            
🗜️ Default bundle mode: gzip

                            
🧾 Signed .torrentchain generated at publish time

                            
✍️ Publisher EVM identity embedded in deploy artifact

                            
✅ Identity/integrity checks applied during load

                        


                        


                        
💬 Direct Messenger: search an address, start a chat

                        

                            Messaging UX started from
                            michal-wrzosek/p2p-chat
                            and replaced its manual offer/answer step entirely. You enter someone's Nostr
                            address, and the encrypted WebRTC invitation is delivered for you through public
                            Nostr relays — no magnet links or key pasting.
                        

                        

                            
🔍 Search by npub, then start the chat

                            
🎁 Invitations sealed and gift-wrapped (NIP-44 / NIP-59)

                            
🙈 SDP, ICE, EVM address and keys never publicly readable

                            
🪪 Peer verification from public key to EVM address

                            
✍️ Per-message signatures verified on receive

                            
🧊 STUN used: stun:stun.l.google.com:19302

                        

                        

                            WebRTC stays the preferred transport. If a direct connection cannot be
                            established, messages fall back to the relays — still signed and ECIES-encrypted
                            exactly as before, with NIP-44 on top. The chat header says which path is in use:
                            P2P · WebRTC or Relay fallback · Nostr.
                        


                        


                        
🛰️ Nostr relays: browser to relay, directly

                        

                            The app talks straight to a pool of public relays over WebSockets. There is no
                            Web25 relay, no proxy and no signalling server — the relay list is configurable
                            and no single relay is required.
                        

                        

                            
🌐 wss://relay.damus.io

                            
🌐 wss://nos.lol

                            
🌐 wss://relay.nostr.band

                            
🌐 wss://relay.snort.social

                            
🧯 Unreachable relays are tolerated automatically

                            
🧬 Every event is re-verified locally; duplicates collapse

                        


                        


                        
🛰️ Publishing to the registry (NIP-35 / DTAN)

                        

                            Once a site bundle is signed, seeded and live, it can also be published as a public
                            NIP-35 torrent event under the category WEB25.cloud / Websites. This is
                            a second, separate Nostr use case from the private Direct Messenger — registry
                            events carry public metadata only.
                        

                        

                            
🗂️ Category tcat:web25.cloud,websites

                            
🔗 Carries the final BitTorrent infohash and the real torrent entries

                            
📦 In gzip mode that is .torrentchain + site.bundle.json.gz

                            
🪪 Mirrors the .torrentchain EVM proof for pre-download checks

                            
✍️ No second EVM signature — only a Nostr signature is added

                            
🌐 Registry relay: wss://relay.dtan.xyz plus generic relays

                        

                        

                            Deployment and registry publication are reported separately, because they are
                            separate outcomes: a site stays Live / Seeding even if every registry
                            relay is unreachable, and Retry Registry Publish resends the identical signed
                            event rather than creating a second entry. The deploy wizard names which key signs
                            what — Sign .torrentchain · EVM for the website, then
                            Sign & publish registry · Nostr for the registry entry.
                        


                        


                        
🔎 Searching the registry

                        

                            The Browse tab has a second mode, Search WEB25 Registry, next to the
                            existing load-by-hash flow. It queries kind: 2003 events in
                            tcat:web25.cloud,websites and nothing else.
                        

                        

                            
🔍 Search by site name, infohash, EVM publisher, or npub

                            
🪪 Each result shows its publisher verification state

                            
🚀 Open reuses the existing WEB25 hash loader

                            
🧯 Registry availability never affects loading by hash

                        

                        

                            A valid Nostr signature only proves who wrote the registry entry. Showing
                            Publisher verified requires the separate mirrored EVM proof to check out, so
                            results appear as verified, invalid, malformed or unverified.
                        

                        

                            Nostr provides registry, discovery and search. Website content is distributed over
                            BitTorrent, and authenticity still comes from .torrentchain after
                            download. When a site is opened from a registry result, the entry is compared against
                            the manifest that actually arrives — any disagreement is surfaced and the registry
                            claim is withdrawn, because the downloaded manifest always wins.
                        


                        


                        
🛡️ Security profile

                        

                            WEB25.cloud validates signed publisher metadata and sanitizes rendered HTML with DOMPurify at load time.
                            The sanitizer is intentionally configured in a compatibility-oriented profile (more permissive than strict defaults)
                            to support richer static websites.
                        

                        

                            
🧾 Signed-manifest verification before render gates

                            
🧼 DOMPurify sanitization applied to loaded HTML

                            
🧩 Extended tag/attribute/protocol allowance for compatibility

                            
⚖️ Explicit trade-off: broader compatibility vs stricter hardening
